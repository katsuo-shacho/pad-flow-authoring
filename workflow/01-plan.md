# 01 計画（プロコードと同じ入口。方針が固まったら GO）

最初の往復で「やりたいこと→要件→方針→見積もり」を1枚にして利用者に見せ、GO をもらってから作る。
質問は一度にまとめ、答えが無ければ既定値を置いて進める（既定値は明記）。

## 1. 要件カード（これを埋める）
- 目的: 何を、誰のために、どれくらいの頻度で（毎日／月末／都度）
- 入力: ソース（Excel／Web／メール／フォルダー）、件数の目安、形式のばらつき
- 出力: 成果物と置き場、成功の判定（何を見れば終わりか）
- 制約: PAD の版、Classic／Power Fx、使えるアクション（拡張機能・ブラウザー・Office）、無人か有人か、認証の扱い
- 禁止事項: 触ってはいけないデータ・送信系アクション・本番フロー
- 現行: 既存フローがあるか（あれば退避して差分で進める）

## 2. 方針（02-design.md の結果を要約）
- 処理順 5〜12 行。一括にする所／ループが残る所／再試行／チェックポイント を明記
- 使うモジュール（knowledge/catalog.md の群名）と、実機で確認が要る部品（UI要素・未収録 ID）
- 検証方法: AI 内の模擬貼付テストまで／エージェントで実機まで／利用者が貼る（04-environments.md）

## 3. 見積もり（ざっくりでよい。根拠を1行ずつ）
- 規模: アクション数の目安、サブフロー数、ループの段数
- 工数: 設計 / 組立 / 模擬テスト / 実機検証 / 取り込み を分けて（AI 側の時間と利用者の立ち会い時間を分ける）
- リスク: 上位3つと回避策（例: ブラウザー拡張の読込失敗→attach 方式、Excel が開きっぱなし→attach を先に）
- 実行時間の見込み: 件数×1件あたり（粗くてよい。後で計測して差し替える）

## 4. GO の条件
- 利用者が「方針・禁止事項・検証方法」に同意。
- GO 後は 02→03→04 と進み、設計の分岐か元に戻せない操作以外では聞かない（06-autonomous-loop.md）。
- 方針が途中で崩れたら（前提が違った、KB に無い部品が中心だった）、作業を止めて計画を1枚に更新し、再 GO を取る。

## 出力の形（これが plan.md。00-modes.md の spec の1つ目）
```
## 計画: <フロー名>
目的 / 入力 / 出力 / 制約 / 禁止
方針（処理順）
見積もり（規模・工数・リスク・実行時間）
検証方法
→ GO でよければ着手します。既定値のまま進めてよい項目: ...
```

## 5. 「PAD でなくてよいのでは」の提案（2回だけ: 構想段階と、最後のハーネス段階）
1回目は計画カードの末尾（作る前）。2回目は出力ゲートを通った後の静的レビューの末尾（作った後。出来上がった Robin の大半がスクリプト1ブロックだった、UI 操作が結局無かった、などが見えた時点）。どちらも PAD より明確に向いている手段があれば**提案だけ**する（決めるのは利用者）。該当が無ければ何も書かない。
判断の軸は「開発環境が要らないか」。PAD を使っている時点で IDE や実行環境は無い前提で、Office と Windows 標準機能で済むものを優先する。

| 手段 | 明確に向くとき（この条件を満たすときだけ提案） | 言い方 |
|---|---|---|
| **Excel マクロ（VBA）** | 入出力がほぼ Excel 内で完結し、UI 操作が不要。ブック内で配布・実行でき、PAD の起動やライセンスが要らない | 「代替案: Excel マクロ — Excel 内で完結し PAD 不要」のように具体的に |
| **VBScript / PowerShell（Windows 標準）** | ファイル・フォルダー・テキスト・CSV の一括処理、Office の COM 操作。画面操作なし。タスク スケジューラで無人実行できる | 「代替案: VBScript — 画面操作が無く標準機能で済む」のように具体的に。PowerShell より VBScript を先に挙げる（実行ポリシーの制約） |
| **ブックマークレット（ブラウザー内 JS）** | 操作対象が Web ページ1枚で、DOM をいじれば済む（値の一括入力、表の抽出、ボタン連打）。拡張機能が入れられない環境でも使える | 「代替案: ブックマークレット — Web 1 ページの DOM 操作のみ」のように具体的に |
| **Office スクリプト / Power Automate クラウド** | SharePoint・Teams・メール等のクラウド側で完結し、デスクトップが不要 | 具体的に |
| **Python / .NET** | 大量データ・複雑な計算・外部ライブラリが必要 | 弱く、条件付きで。「もし会社の PC に Python を入れられるなら、Python の方が一般的で楽です。インストールに申請や制約があるなら PAD で進めて問題ありません」のように、インストール可否を前提条件として明示する |

PAD が向くのは、デスクトップアプリや旧 Web システムの画面操作が避けられない、複数アプリをまたぐ、利用者が GUI で起動したい、のいずれか。これらが無いときだけ上の提案を出す。
提案の形: 「技術選定メモ: <手段>。<何がどう楽になるかを具体的に1〜2文>。<前提・条件を1文>」の短い一段落（3文まで）。見積もりや比較表は書かない。実装中（組立・検査の途中）には出さない。主導権は開発者にあり（会社の環境を踏まえて PAD を選んでいる前提）、返事が無ければ PAD 版をそのまま進める。目的は無駄な開発を一言で止められるようにすること。本線（PAD の設計・組立）を脱線させない。
