# 07 既存フローの改善（「速くしたい」「壊れにくくしたい」の入口）

新規作成（01→06）ではなく、動いているフローを渡されたときはここから。目標を**速度**か**精度（壊れにくさ）**かで分けて、1周1変更で回す。

## 0. 受け取り（必ず）
- 現行の Robin（手編集を含む）を退避し、戻し先を確保する。デザイナーからコピーしたテキストが正。配布ソースを正とみなさない。
- PAD の版、Classic／Power Fx、UI 要素リポジトリの有無、実行の仕方（コンソール／デザイナー／クラウド起動）を聞く。
- 目標を1文で: 「何分→何分」「何件中何件失敗→0」。測れない目標は測れる形に直してから。

## 1. 現状を機械的に見る（AI 内で完結）
- `scripts/robin_lint.py` の FATAL/ERROR/ADVICE（Chat モードでは silent-kills.md と 03-principles を当てて手で判定）。
- `scripts/robin_to_mermaid.py` で構造を見る: ループの段数、ループ本体のアクション数、UI 要素依存の行の割合、WAIT の数、サブフロー数。
- 設定が REGION 00/01/02 に集約されているか（patterns-config-object.md）。散っていれば最初の候補はこれ。

## 2. 速度なら
- 計測が先。コンソール実行のアクション履歴（debug-facts.md）か、区間ごとの時刻ログを `scripts/analyze_timing.py` へ。待機を除いた純処理時間で、粗→細。
- 効く順: ループ本体の削減 ＞ 固定 WAIT の除去 ＞ UI 操作の JS／スクリプト置換 ＞ ブラウザー内で完結（patterns-browser-fetch.md） ＞ サブフロー整理。
- 採用判定: 同条件で純処理が短く、失敗率が上がらず、アクション数が増えない（06）。

## 3. 精度（壊れにくさ）なら
- 失敗の記録を集める: エラー ペインの場所と例外名、Get last error の内容、ローカル実行ログの最後のアクション（debug-facts.md）。
- 原因の型で分ける:
  - **環境依存**（パス・URL・セレクター・ウィンドウ名）→ REGION 00 に集約、UI 要素は一意な識別子だけ（03 の優先順位）
  - **タイミング**（固定 WAIT、読込前に操作）→ 条件付き待機＋実時間の上限（browser-fetch 4）
  - **データ**（空・型違い・末尾空白・全角）→ 入口で正規化、0件は早期終了
  - **外部要因**（ネットワーク・アプリの一時失敗）→ その行だけ `ON ERROR REPEAT`、全体を囲まない
  - **論理**（添字範囲外、未定義変数）→ ブロック エラーで捕まえ、フラグで後段分岐
- 最終照合を件数一致から3点（存在・サイズ・予定外なし）へ（browser-fetch 8）。

## 4. 提案の出し方
- 候補を「効果 × 手間 × リスク」で並べ、上位3つを「変更・期待効果・リスク・戻し方」各1行で。
- 1周1変更。変更ごとに lint → 検証用フロー（05）→ 計測 → 採用／不採用を記録。
- 最後に技術選定メモ（01 の基準）: 出来上がりの大半がスクリプト1ブロックなら、PAD を外す案を1段落添える。主導権は開発者。
