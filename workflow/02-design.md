# 設計から入る（Robin を書く前に）

PAD は手で積むツールなので、作る人の頭から「アルゴリズム」が抜けやすい。AI 側はそこが得意なので、
コードの前に必ずこの順で設計を固め、利用者に1回だけ確認する（長い質問攻めはしない）。

## 0. 仕様を3行で
- 入力（何を・どこから・件数の目安）／出力（何を・どこへ）／成功の判定（何を見れば終わったと言えるか）。
- 「毎回全部やり直す」のか「差分だけ」なのか。途中で止まったら「最初から」か「続きから」か。

## 1. データの流れを先に決める（アクションはまだ選ばない）
- 一覧を**最初に一括取得**し（ファイル一覧、Excel 範囲、Web テーブル、メール一覧）、その上で判断する。1件ずつ取りに行かない。
- 変換・集計・整形は**1か所にまとめる**（データテーブル操作、PowerShell、JS）。UI 操作の間に点在させない。
- 書き戻しも**一括**（データテーブルを Excel に1回で、ファイルは最後にまとめて移動）。
- 外部の状態（ブラウザー、Excel インスタンス、ファイル）に触る区間を最小にし、その前後で変数に閉じる。

## 2. アルゴリズムの型を選ぶ（よく効く順）
- **フィルター→一括処理**: 対象を絞ってからまとめて処理。ループ不要になることが多い。
- **突き合わせ**: 2つの一覧をキーで結合する。ループの入れ子（O(n²)）にせず、一方をキー付き（カスタムオブジェクト／データテーブル検索）にして一重ループにする。
- **チェックポイント**: 件数が多い・途中で落ちる可能性がある処理は「処理済み一覧」をファイルに書き、再実行時は未処理だけを対象にする（冪等）。
- **再試行は局所に**: 落ちるのは外部要因の行だけ。その行に `ON ERROR REPEAT n TIMES WAIT s`。全体を囲まない。
- **受付と完了確認の分離**: ダウンロードや外部処理のように「依頼」と「完了」が別のタイミングになる処理は、予定一覧を先に確定し、受付→完了監視→最終照合を分け、移動・改名は照合済みのものだけ最後に一括で行う（例: knowledge/patterns-download-pipeline.md）。
- **早期終了**: 入力が空・前提ファイルが無い・既に処理済み、は冒頭で判定して抜ける。
- **状態の確認で待つ**: 固定 WAIT ではなく「出現／存在／件数」を条件に待つ（上限付き）。

## 3. 堅牢性チェック（設計段階で潰す）
- 入力が0件／1件／想定外の型（空セル、全角数字、末尾空白）のとき何が起きるか。
- 同名ファイル・既存ワークブックが開いている・ブラウザーが既に起動している、のときの振る舞い（attach を先に試す）。
- 失敗した行を**記録して続行**するか**止める**か。利用者に出すのは最後に1回。
- 認証情報・固定パスは入力変数か設定ファイルへ。

## 4. 速度チェック（設計段階で決める）
- ループ本体は「判断1つ＋処理1つ」程度に。それ以上はスクリプト1ブロックへ寄せる。
- ループ内の SET・型変換・ダイアログ・WAIT・Excel セル単位 I/O を禁止する。
- 画面操作は最後の手段。同じことが HTTP／JS／PowerShell／COM でできないか先に見る。使うなら「何で一意に取れるか」（AutomationId / id / name / data-*）を設計に1行書く。位置・文言・座標・画像に頼る指定は避ける（03-principles.md「UI 要素は最後の手段」）。

## 5. 設計の出し方
- 箇条書きの処理順（5〜12行）＋ 分岐と繰り返しだけを描いたフローチャート（`scripts/robin_to_mermaid.py` は実装後の確認用。設計段階は Mermaid を手書きでよい）。
- 「ここは一括」「ここだけループ」「ここで再試行」「ここでチェックポイント」を明記する。
- 利用者の確認は1往復で済ませる。確認が取れてから knowledge/robin/ を引いて Robin を組む。

## 6. 操作手段の選定（UI 要素とショートカットの配分は毎回「議論」して決める）
外部に触る操作ごとに候補を並べ、固定ルールではなく比較で決める。決めた理由を design.md に残し、検証で壊れたら表に戻って次の候補へ降りる（06 のループで見直す）。

| 操作 | 候補（上が優先） | 安定性 | 速さ | 実装・検証の手間 | 採用 | 理由／条件 |
|---|---|---|---|---|---|---|
| 例: Excel の値取得 | 専用アクション / COM / UI | 高/高/低 | 高/高/低 | 小/中/大 | 専用アクション | — |
| 例: 旧 Web システムの検索 | HTTP / JS / ショートカット / UI | 高/中/中/低 | 高/高/中/低 | 中/中/小/大 | JS→失敗時 UI | 認証後の URL が取れるか要確認 |

判断の勘所（議論の論点をそのまま書く）:
- **ショートカットが勝つとき**: アプリに確実なショートカットがあり、フォーカスを `Focus window` で確保でき、モーダルが出ない操作（保存・次へ・検索ボックスへ移動）。文言や DOM の変更に影響されない。
- **ショートカットが負けるとき**: フォーカス先が不確定（複数ウィンドウ・IME の状態・同名ウィンドウ）、キー割当がアプリの版や設定で変わる、送った後の完了が画面でしか分からない（＝結局 UI 要素の出現待ちが要る）。
- **UI 要素が勝つとき**: AutomationId / id / name で一意に取れ、完了の判定もその要素で取れる。操作と判定を同じ要素で閉じられるなら、ショートカット＋別の判定より壊れにくい。
- **UI 要素が負けるとき**: 一意な識別子が無く位置・文言に頼る、言語や解像度で変わる、要素の取得に録画が要り環境ごとに取り直しになる。
- **混ぜ方**: 「移動はショートカット、判定は UI 要素（確実なもの）」「本命は JS、保険として UI」のように役割で分ける。保険の経路は `ON ERROR` の中ではなく、フラグを立てて後段で分岐する（ハンドラー内に IF は書けない）。
- **配分の目安**: 1フローで UI 要素に依存する行は全体の1割以下、かつ1サブフローに集約。超えるなら「UI 操作を減らす設計」に戻す。
- 迷ったら**検証しやすい方**を先に試す（ダミーフローで単体確認できる方）。結果で決めて、理由を残す。
