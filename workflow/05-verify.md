# テスト・GUI待ち・時間短縮

（自分の環境での実測知見はここに追記する。）

## 2つの入口: デバッグ用と本番用
本番フローは利用者操作（開始確認・途中確認・完了通知・カスタムフォーム）を含む。検証ではそれが毎回の手動クリックになり、検証の自動化を壊す。そこで入口を分ける。

- **入口切替の実装**: 入力変数 `DebugMode`（既定 False）または環境変数/マーカーファイルで判定し、利用者ダイアログを `IF DebugMode = False THEN ... END` で囲む。ダイアログの戻り値（ButtonPressed, UserInput）はデバッグ時に既定値を `SET` で与える。
- **本番ボタンは消さない**: 本番の利用者操作は仕様の一部。デバッグ用入口は「同じ本体を、ダイアログを飛ばして」通す。本体を2本持たない。
- **本番の最終確認は利用者がやる**: デバッグ入口で通っても、本番入口（ボタンを実際に押す経路）の確認は省略しない。
- **終了ボタン**: 完了通知ダイアログは、検証時はタイムアウト付き（`ShowMessageWithTimeout`）または DebugMode で省略し、自動実行が止まらないようにする。本番では利用者が押す。
- **ユーザー操作の代行ツール**: 画面の確認・ボタン押下が検証に必要な場合は、計算機操作（computer use / 自前のUIオートメーション）でそのボタンだけ押す補助を用意する。本体フローを書き換えてボタンを消す形で代用しない。

## 検証の段階
1. **構文**: 生成したテキストを、ダミー専用フロー（例 `ZZ_Paste_Test`）に貼る。貼付成功＝構文OK。実行はしない。
2. **エンジン**: ダミーフローで UI を伴わない部分（変数・ファイル・スクリプト）だけ実行。入力は固定のテストデータ。
3. **画面**: 実フローのデバッグ入口で通す。ブレークポイント・「ここから実行」（公式 debugging-flow）を使い、失敗点だけ再実行する。
4. **本番**: 利用者操作込みで1回通す。終わったらログ・一時ファイル・テスト専用フローを配布物から外す。
- v2.54 以降・Premium があれば公式テストケース（Test a desktop flow + Assert）で 2〜3 を自動化できる。`%Out = 25%` 形式の式で出力変数を検証。

## 合否の判定
- 出力変数、生成ファイル（存在・サイズ・行数）、Excel の特定セル、ログ末尾の文字列、のどれかを「期待値ファイル」と突き合わせる。目視だけで合格にしない。
- 期待値ファイルは `tests/` に置き、フロー側は `File.ReadTextFromFile` 等で読んで比較する。

## 待機の設計
- 固定 `WAIT` は禁止寄り。`WAIT (UIAutomation.WaitForWindow...) FOR n` / `Wait for web page content` / `Wait for file` の条件付き待機に置き換え、`FOR` の上限を必ず付ける。
- ネットワーク・外部アプリ起因の失敗は `ON ERROR REPEAT n TIMES WAIT s` で吸収し、n×s を記録する（再試行で隠した失敗は報告に書く）。
- ウィンドウのフォーカス・前面化が必要な操作は `Focus window` を明示する（公式 how-to/ensure-windows-become-focused）。

## 時間短縮
- 計測してから変える。Designer の実行ログ（アクションごとの時間）または `Get current date and time` をループ前後に置いて差分を取る。
- 最適化は同条件（同データ・同マシン・同時刻帯）での実測差分だけを採用する。「速そう」で変えない。
- 典型的な効果順: ループ内アクション削減 > 固定WAIT除去 > UI操作のJS/スクリプト置換 > サブフロー整理。

## 検証に使わないもの
- 本番データ・本番の保存先。テストは専用フォルダーと専用フローで行う。
- 認証情報の平文。テスト用もマーク済みの機密変数か暗号化入力にする。
