# 08 デバッグ（「動かない」「途中で止まる」「たまに失敗する」の入口）

目的は「どの行で・どの条件で・なぜ」を1文で言えるようにすること。直すのはその後（07 へ）。

## 0. 症状を3種類に分ける
| 症状 | まず見る所 | 典型原因 |
|---|---|---|
| **貼れない**（キャンバスが空、または赤い行） | silent-kills.md、robin-rules.md | 予約語、文字列外の `%`、ハンドラー内の禁止文、ID の版差、ヘッダー行 |
| **起動しない／最初で止まる**（設計時エラー） | エラー ペインの Type=Error、Line | 必須引数が空、未定義変数、UI 要素リポジトリ未貼付 |
| **途中で落ちる／たまに失敗** | エラー ペインの例外名と行、Get last error、ローカル実行ログ（debug-facts.md） | 環境依存・タイミング・データ・外部要因・論理（07 の型） |

## 1. 再現の最小化
- 入力を最小にする（1件・1行・1ファイル）。それでも落ちるか。
- 「ここから実行」で失敗行の直前から走らせ、変数ペインで入力値を見る。前段の変数が要るなら SET で仮置き。
- ブレークポイントを失敗行の**前**に置き、「次のアクションを実行」で1行ずつ。値が期待と違う最初の行が原因。
- たまに失敗するものは、固定 WAIT を疑う。実時間で上限を持つ条件待ちに置き換えて再現頻度を見る（browser-fetch 4）。

## 2. 情報の集め方（利用者に頼む形で書く）
- エラー ペインをダブルクリックした内容: メッセージ、場所（サブフロー・行・アクション）、エラー詳細の先頭数行。
- 失敗行の Robin（その行と前後2行）。
- ローカル実行ログの最後の数アクション（時刻・名前・結果）。パスは debug-facts.md。
- 環境: PAD 版、Classic／Power Fx、実行の仕方（コンソール／デザイナー／クラウド）、ブラウザーと拡張機能の版。
- 会社固有の値（URL・パス・ユーザー名）は伏せ字で。

## 3. 原因の言い方
「<サブフロー>:<行> の <アクション> が、<条件>のとき <例外名> で止まる。原因は <型: 環境依存／タイミング／データ／外部要因／論理>。」
この1文が書けたら 07 の「精度」へ。書けないなら 1 に戻る。

## 4. 直したあと
- 同じ入力で再現しないこと＋別の入力で壊れていないことを、検証用フロー（05）で確認。
- 踏んだものは silent-kills.md（貼付系）か patterns-*.md（設計系）に1件追記。「症状 → 原因 → 直し方 → 検査方法」。

## 道具
- エージェント環境: `scripts/robin_lint.py`（貼付系）、`scripts/robin_to_mermaid.py`（構造）、`scripts/analyze_timing.py`（時間）。
- Chat モード: silent-kills.md の正規表現検査を手で当て、結果を一言報告。
